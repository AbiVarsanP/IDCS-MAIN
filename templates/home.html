About this website

Overview

  • IDCS appears to be an academic/student services portal with role-based interfaces (students, staff, HOD, AHOD) plus public pages and admin functions.
  • Templates are organized by role and feature; each template corresponds to views that render pages for that role or feature.

Public / site-wide pages

  • home.html — Landing page / homepage (hero, notices, posters).
  • about.html — About the college / site.
  • academics.html — General academics info page.
  • transport.html — Transport information.
  • feedbackform.html — Public feedback submission form.

Authentication

  • auth/login.html — Login page for all users.

Common / shared pages

  • common/profile.html — Profile page used by multiple roles (view/edit profile).

Admin / management

  • admin/core/import_students.html — Admin UI for bulk student import.
  • admin/core/student_changelist.html — Django admin list view customization for students.
  • admin/core/academicrecord/change_form.html — Admin change form for academic records.

Role-based applications

  • student/ — Templates for student users (dashboard, attendance, timetable, forms like bonafide, gatepass, leave, od).
  • staff/ — Templates for staff users (dashboard, requests handling, class management, notifications).
  • hod/ — Head of Department templates (approvals, mentee lists, HOD dashboard).
  • ahod/ — Assistant HOD templates (similar to HOD with narrower scope).

Feature-specific pages

  • Feedback pages, gatepass and bonafide apply/approve templates, on-duty forms (od/ods), and notification history pages.

How these pieces map to the codebase

  • Each template folder likely corresponds to a Django app or view namespace (student, staff, hod, ahod, common, admin).
  • Views render these templates and enforce role-based access (login_required + permission checks).
  • Static assets live under core/static/ and are referenced via {% templatetag openblock %} static 'path/to/file' {% templatetag closeblock %}.
  • admin/ contains customized admin templates or overrides for Django admin.

Next useful actions

Possible next steps include creating a README describing routes/templates to views, mapping templates to view names by scanning the project, editing any template content, or generating a role-permissions matrix.
